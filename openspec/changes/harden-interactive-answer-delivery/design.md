## Context

See `proposal.md` for motivation and `specs/interactive-steps/spec.md` for observable behavior. Asking runs persist `pending_question` on the run, but `Engine.answer` currently clears that column transactionally before calling the runner session prompt. Concurrency is guarded, yet a daemon crash after the clear and before the external side effect loses an already accepted human decision.

The existing completion-decision outbox establishes the repository's confirmation-of-effect pattern. The answer path needs the same durable intent/confirmed-effect split without moving runner I/O into the pure interpreter or changing the HTTP answer payload.

## Goals / Non-Goals

**Goals:**

- Make operator acceptance atomic and durable before runner I/O.
- Resume incomplete answer delivery during ordinary reconciliation after restart.
- Preserve one accepted answer per question under request races and retries.
- Keep aggregate human-attention projection correct while an answer is accepted but not yet confirmed delivered.
- Retain accepted notes and final delivery disposition for audit.

**Non-Goals:**

- Exactly-once execution by an arbitrary runner transport that provides no idempotency primitive.
- New workflow syntax, web forms, CLI commands, or runner capabilities.
- Changing idle/TTL policy for asking runs.
- Refactoring the general scheduler, retry engine, or completion-decision outbox.

## Decisions

### Persist answer delivery intent as a first-class durable record

Add an additive answer-delivery record keyed by run and question generation. It stores accepted notes, target session, state, timestamps, bounded failure detail, and an idempotency token generated by Conductor. Acceptance and the transition-log entry occur in one transaction guarded by the run still being active and asking.

The question remains visible and the feature remains `waiting_human` while delivery is pending. Confirmation atomically marks delivery complete, clears the corresponding question, recalculates aggregate human attention, and records the answer transition.

Alternative: retain notes in process memory and clear after prompt. Rejected because a restart loses the accepted answer. Alternative: overwrite `pending_question` with a tagged answer payload. Rejected because it conflates operator-visible question state, delivery intent, audit history, and retry metadata.

### Reconciliation owns restart recovery; the engine owns the prompt side effect

`Engine.answer` claims the durable delivery after acceptance and attempts it immediately for low latency. The reconciler also claims pending deliveries so startup and heartbeat processing repair crashes. Claims are conditional and leased/bounded so concurrent reconcile cycles do not issue the same prompt simultaneously.

The interpreter is unchanged and remains pure. The store owns atomic acceptance, claim, completion, and failure transitions. The engine remains the only owner of session status and prompt I/O.

Alternative: deliver synchronously before committing acceptance. Rejected because a successful prompt followed by a database failure permits a second human answer and duplicate decisions. Alternative: rely only on the request handler to retry. Rejected because clients cannot know whether a daemon crashed after acceptance.

### Treat confirmation strength as a runner boundary

The first implementation uses the existing session prompt operation and a stable Conductor delivery token in the prompt. Store claims prevent concurrent duplicates, but a crash after the runner accepts the prompt and before the database marks it delivered remains an at-least-once edge unless the runner adapter can deduplicate the token. The opencode adapter SHALL preserve the token in the delivered prompt and tests SHALL cover both sides of the database/runner boundary.

Alternative: claim transport-level exactly-once without runner support. Rejected because SQLite cannot atomically commit with an external session service. A later runner-protocol capability may make the idempotency token authoritative across adapters.

### Terminal delivery failure follows existing run failure routing

A confirmed missing session or terminal prompt error concludes the active run through the existing classified failure path. The answer-delivery record is retained with its failure disposition. Transient infrastructure errors keep the delivery pending for bounded reconciliation rather than clearing the question or silently concluding success.

Alternative: recreate a session automatically. Rejected because the requirement is to continue the same contextual session and ordinary step retry policy already defines honest recovery after session loss.

### Repeated answer while accepted-pending is a conflict, not an idempotent success

A second answer request for the same question while a prior delivery is accepted-but-undelivered is rejected with the same conflict-class error as answering a non-asking run. It does not replace the accepted notes and never creates a second delivery for the same run — the partial unique index enforces at most one non-terminal delivery per run at the database layer, and `Engine.answer` maps the store's `already_accepted` outcome onto the existing `no_pending_question` wire code rather than inventing a new one. This is deliberately NOT treated as an idempotent retry: the current answer contract carries no caller-supplied idempotency key, so there is no way to distinguish "the same client retrying" from "a different operator racing a stale view" — treating either as success-with-no-op would silently discard a distinct decision if the two callers actually disagreed. The wire contract is unchanged by this decision.

### Pause blocks the delivery side effect, not acceptance

Acceptance is a durable state transition and is allowed while a feature is paused, exactly like any other durable-state write not gated on the runner. The runner prompt side effect is a different matter: it is never attempted while the feature is paused, whether requested immediately (`Engine.answer`) or during reconciliation. This mirrors the retry-policy pause barrier already enforced for retry-episode and resource-wait due-work (`listDueRetryEpisodes`/`listDueResourceWaits`/their claim counterparts all exclude paused features) — `listPendingAnswerDeliveries`/`claimAnswerDelivery` apply the identical join-and-exclude guard. A delivery accepted while paused sits `pending` until the feature resumes and a reconcile pass claims it; no operator resubmission is required.

## Risks / Trade-offs

- [Runner prompt lacks transport idempotency] -> include a stable delivery token, prevent concurrent claims, document the narrow at-least-once crash edge, and evolve runner protocol separately if true deduplication is required.
- [Accepted answer remains visibly actionable during delivery] -> project a pending-delivery state that disables resubmission while retaining the original question and human-attention status.
- [A poisoned delivery retries forever] -> classify prompt failures and use bounded claim/retry timing before terminal failure routing.
- [Migration encounters already asking runs] -> create no delivery row until an answer is accepted; existing pending questions require no rewrite.
- [Pause or run conclusion races with delivery] -> claim and completion transactions re-check active run/question identity and leave a durable cancelled/failed disposition when the target no longer accepts delivery.

## Migration Plan

1. Add the answer-delivery table/indexes without rewriting existing runs.
2. Deploy store acceptance/claim/completion operations and reconciliation before routing API answers through them.
3. Enable immediate delivery from `Engine.answer`, backed by the same reconciler path.
4. Verify crash boundaries before acceptance, after acceptance, after runner prompt, and after confirmation.
5. Rollback only after no pending answer deliveries remain; otherwise retain the upgraded daemon until they reach a terminal disposition.
