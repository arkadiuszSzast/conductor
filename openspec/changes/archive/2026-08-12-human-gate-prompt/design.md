# Design — human gate prompts

## Context

See proposal.md — Why. Current state that shapes the design:

- `HumanStep` is an empty marker (`{ type: "human" }`,
  `packages/core/src/types.ts:128`); the parser accepts `human: {}` only.
- Gates arm in the interpreter by setting step/feature status to
  `waiting_human` (`interpret.ts` — entry dispatch, `onCompleted` routing,
  rerun re-arm). The interpreter is pure: it cannot render (rendering reads
  live state and must be a side-effect-free decision).
- Agent prompts are rendered engine-side at dispatch time via
  `buildEvalContext` + `renderTemplate` (`engine.ts:232-234`); render errors
  log and the incomplete text is not dispatched.
- `StepRuntime.outputs` is the persisted per-step record; gate decisions
  already write `notes` into it through `resolveGates`.
- The feature detail projection (`api-ui-projections`) lists steps with
  status; the web gate panel (`apps/web/src/gate/`) shows only the step name.

## Goals / Non-Goals

**Goals**
- One new optional IR field; zero interpreter semantics changes.
- The approver sees the rendered question wherever gates are decided
  (web UI, CLI, API consumers).
- Restart-safe: the rendered text lives in SQLite, not in memory.

**Non-Goals**
- Interactive/multi-turn Q&A with a running agent session (a different,
  larger feature — session interactivity).
- Typed answer schemas in the engine or API. Structured questions are a
  **presentation convention** (D6); the engine/API contract stays
  "prompt text in, notes text out".
- Markdown rendering in the UI (plain text now; formatting later if needed).

## Decisions

### D1 — Render in the engine when it applies the arming transition

The interpreter stays pure: it decides "this step is now `waiting_human`".
The engine, after `store.applyTransition`, detects steps that just entered
`waiting_human`, renders their `prompt` (if declared) with
`buildEvalContext` (including the feedback snapshot when the arm happens
inside a rerun round), and persists the result.

*Alternative considered*: render lazily in the API on read. Rejected —
re-rendering on every read repeats work, needs feedback snapshots retained
for reads, and can drift if state mutates between reads; arm-time rendering
matches agent-prompt semantics ("the context the step was dispatched with").

### D2 — Persist the rendered prompt as a step output (`prompt`)

Store the rendered text in the existing `StepRuntime.outputs` map under the
reserved key `prompt`, written when the gate arms. No schema migration; it
rides the same persistence, projection and reset paths as other outputs —
a rerun that clears the step clears the stale prompt with it, and the
re-arm re-renders it (spec: re-render per round).

On decision, `resolveGates` merges `notes` into outputs; the write MUST
preserve the existing `prompt` key (today it replaces outputs wholesale
with `{ notes }` — adjust to merge).

*Alternative considered*: a dedicated column/table keyed by feature+step.
Rejected — more surface (migration, projection plumbing) for no added
behaviour; outputs already flow everywhere the prompt needs to go.

*Consequence*: `steps.<gate>.outputs.prompt` becomes readable in
expressions. That is acceptable (it is honest data), but validation keeps
advertising only `notes` for human steps to avoid encouraging coupling; the
docs note `prompt` as reserved.

### D3 — Validation reuses the agent-prompt rules verbatim

`validate.ts` already checks agent `prompt` templates (syntax, earlier-step
references, known output names, declared `needs` outputs). The same checks
run for `human.prompt`; the only difference is the step kind carrying the
field. Feedback references follow the existing feedback-legality rule
(legal iff a rerun targets the job).

### D4 — Render errors never block the gate

A gate exists to hand control to a human; a broken template must not stop
that. Failed expressions render as empty (existing `renderTemplate`
contract), errors go to the log, the gate arms and shows the partial text.
This mirrors the agent-prompt error posture (log + continue) rather than
the action-input posture (fail the step) because no downstream automation
consumes the prompt.

### D5 — Projection shape: `prompt` on the step entry of the detail view

Feature detail step entries gain an optional `prompt` string, present only
when the step is `waiting_human` at read time and a rendered prompt exists.
CLI `status <id>` prints it under the gate line. The web gate panel shows
it as pre-wrapped plain text above the decision controls.

### D6 — Structured questions are a client-side convention over the prompt

Questions are generated by agents at runtime, so they arrive embedded in
prompt text (an agent writes them into its report; the gate prompt quotes
the report). The convention: a fenced block tagged `conductor-questions`
containing a JSON array of `{ "question": string, "options"?: string[] }`.
The web UI detects and parses the block (a pure function, unit-testable),
renders option pickers + a custom-answer text field per question, and
composes the decision notes as plain-text Q/A pairs. Parsing failures fall
back to the plain-text prompt.

Agents are steered to emit the block by workflow prompt instructions (the
workflow author asks the explorer to end its report with the block) — no
engine or runner changes.

*Alternatives considered*:
- Typed `questions` field on `HumanStep` in YAML — rejected: questions are
  runtime data from agents, not static workflow data; a static field cannot
  carry them and would invite double semantics.
- Structured answers in the API (`answers: [...]` on the decision) —
  rejected for this change: it forks the notes contract every consumer
  (engine feedback, expressions, CLI) already understands. Plain-text Q/A
  pairs in notes carry the same information to downstream agent prompts.
  Revisit if a machine consumer ever needs unserialised answers.

## Risks / Trade-offs

- **Reserved output-key collision**: a hypothetical runner reporting a
  `prompt` output for a human step would be overwritten at arm time. Human
  steps have no runner today; documented as reserved.
- **Prompt staleness inside a round**: the prompt reflects arm-time state;
  if later parallel jobs finish while the gate waits, the text does not
  update. Accepted — same semantics as agent prompts.
- **Merge-not-replace in `resolveGates`**: small behavioural change to how
  gate outputs are written; covered by a regression test (notes preserved,
  prompt preserved).
- **Agents may emit a malformed questions block**: the convention degrades
  to plain text by design, so the gate still works; the answer form is a
  progressive enhancement, not a dependency.

## Migration Plan

None required — additive optional field, no DB schema change, existing
workflows and stored features unaffected. Rollback = revert; persisted
`prompt` outputs on old features are inert extra keys.

## Open Questions

None — sized and settled for implementation.
